# ApeShareCore как библиотека

Общая реализация находится в [ISAIandCO/ApeShareCore](https://github.com/ISAIandCO/ApeShareCore). В расширении больше нет копии `src/shared/core`, lock-файла этой копии или команды переноса исходников между расширениями.

Пакет `@isaiandco/ape-share-core` подключён через `package.json` и `package-lock.json` к архиву **конкретного Git-коммита**. Lock также содержит integrity архива. Обычный `npm ci` устанавливает ту же библиотеку на чистой машине; соседний checkout ApeShareCore не нужен. Использование архива по HTTPS не требует SSH-ключа или публикации в npm registry.

Библиотека включается в сборку. Установленное расширение не загружает код из GitHub, не нуждается в npm и не обновляет ядро само. В сборку включена лицензия библиотеки.

## Подключённые модули

| Модуль ApeShareCore | Использование |
|---|---|
| ioc/client, providers, normalize | Клиенты четырёх внешних API, типы и каталог провайдеров |
| ioc/ui | Общая логика кнопок проверки в существующих меню; запросы и отображение результата передаются callback-функциями |
| values/ip, hash, url | Нормализация значений |
| ai/transport | HTTP-транспорт AI с точным payload и необязательным ключом |
| ui/markdown | Отображение ответа AI |
| events/compare | Сравнение событий с продуктовой группировкой полей |
| graph/force-layout, spatial-index | Алгоритмы графа |
| ai/chat, investigation/model, ioc/batch | Уже используются ApePatrol; доступны KumApe для последующего подключения |

У расширения остаются SIEM DOM/API, SQL/PDQL, поля и категории событий, ключи и permissions, маршруты вкладок, persistence, сбор AI payload и контекст инструментов. Импорты через старые продуктовые модули сохранены там, где это предотвращает ненужные изменения вызывающего кода.

Модели чата и расследования ApePatrol перенесены без изменения формата данных. Его `eventAiAttachment` остаётся в адаптере: знание полей event_src/time/uuid не попало в библиотеку. Форматы истории и расследования KumApe сейчас не меняются.

## Проверка и обновление

```sh
npm ci
npm run core:check
npm run test:core
npm test
```

`core:check` проверяет закреплённый SHA, согласованность package/lock и установленную версию. После сборки `node scripts/check-core.mjs --built` дополнительно проверяет отсутствие неразрешённых импортов пакета в Firefox-артефакте. Контрактные тесты потребителя проверяют именно установленную версию библиотеки.

```sh
npm run core:update
```

Команда читает `main` ApeShareCore и обновляет зависимость только на **более новую версию 1.x**. Она закрепляет точный SHA, обновляет integrity lock-файла и поднимает patch-версию расширения. Изменение major требует ручной адаптации. Повторный запуск без новой версии ничего не меняет; поэтому при изменении runtime-кода библиотеки нужно поднимать её версию.

Workflow `Update ApeShareCore` запускается ежедневно в 04:41 UTC или вручную. Он проверяет кандидат контрактными тестами, тестами продукта и сборкой, затем создаёт PR. Дополнительно запускается обычный CI на новой ветке, поскольку PR от GITHUB_TOKEN сам по себе не запускает pull_request workflows. Автомержа нет; неуспешный кандидат не меняет `main` и установленное расширение. Для одной версии используется одна ветка обновления. Возможность создавать PR должна быть разрешена в Actions settings репозитория.

В самой библиотеке workflow `Consumer compatibility` проверяет кандидата на подключённых версиях расширений из `main`. Таким образом, изменение общей реализации сначала проверяется на стороне библиотеки, а принятие новой зависимости — на стороне каждого потребителя.

## Порядок первоначального внедрения

Сначала слить PR ApeShareCore с пакетом, затем PR подключения расширений. Они закреплены на опубликованном коммите библиотеки и собираются независимо; автоматическая проверка новых версий начинает работать после появления package.json библиотеки в её `main`.

Публичные API, побочные эффекты и правила изменения схем описаны в [CONTRACTS.md](https://github.com/ISAIandCO/ApeShareCore/blob/main/CONTRACTS.md). Автономность означает отсутствие скрытой зависимости от конкретного расширения. Она обеспечивается входными данными, callback-интерфейсами и тестами, а не предположением, что любое внутреннее изменение всегда безопасно.
